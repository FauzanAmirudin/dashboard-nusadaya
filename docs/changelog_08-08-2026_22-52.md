# Dokumentasi Sistem Storage & Prosedur Restore Backup
**Dashboard Nusadaya (v2.0)**

Sistem penyimpanan dan backup pada Dashboard Nusadaya telah direstrukturisasi total untuk menjamin **keamanan, kecepatan (asynchronous), dan skalabilitas tingkat enterprise**.

---

## 1. Arsitektur Storage & Backup Baru

Perubahan terbesar yang telah dilakukan pada sistem ini meliputi:

### A. Storage Di Luar Source Code
File-file aplikasi (foto, PDF, nilai, dll.) **tidak lagi disimpan di dalam `apps/api/uploads`**. 
- **Di lokal (tanpa Docker):** File otomatis tersimpan di folder root proyek yaitu `C:\.PROJECT\dashboard-nusadaya\storage\` dan `\backups\`.
- **Di server (via Docker):** File diamankan di dalam **Docker Volume** independen (`academic_storage` dan `academic_backups`) yang di-mapping ke `/app/storage` dan `/app/backups`.

### B. Background Workers & Redis Queue
Proses backup yang berat sekarang ditangani secara **asynchronous**.
1. Saat backup diminta (otomatis via jadwal atau manual via Admin), API akan mencatatnya di PostgreSQL (`backup_jobs`) dan memasukkannya ke antrean **Redis** (`queue:backup`).
2. API langsung merespons sukses dengan `jobId` dalam hitungan milidetik.
3. Di latar belakang, **Backup Worker** akan mengambil tugas tersebut, memasang *Redis Lock* (mencegah backup ganda), dan mulai menyalin ribuan file tanpa membuat API *hang*.
4. Progress penyalinan (persentase) dikirim ke Redis secara *real-time* untuk ditampilkan di UI.

### C. Keamanan Integritas Data (Manifest)
Setiap backup yang dihasilkan wajib memiliki file **`manifest.json`**. File ini berisi:
- Metadata ukuran total dan jumlah file.
- Checksum **SHA-256** untuk setiap file fisik sebagai sidik jari digital (mencegah korupsi data).

## 2. Struktur Direktori Backup

```text
backups/
├── students/
│   └── {studentId}/
│       └── {timestamp}-{jobId-suffix}/
│           ├── manifest.json
│           └── students/{studentId}/{category}/{filename}
├── cohorts/
│   └── {cohortId}/
├── programs/
│   └── {programId}/
├── full/
│   └── {timestamp}-{jobId-suffix}/
│       ├── manifest.json
│       └── students/...
└── database/                          # Hasil pg_dump
```

## 3. Verifikasi Integritas Backup

Sebelum melakukan pemulihan (restore) data, Anda **WAJIB** memverifikasi integritas file menggunakan `manifest.json`.

```bash
# 1. Baca manifest (Contoh Linux/WSL)
cat backups/full/{timestamp}/manifest.json | jq '.files[] | .path, .checksum'

# 2. Verifikasi checksum satu file secara manual
sha256sum backups/full/{timestamp}/students/42/identity/01KABC.pdf

# 3. Bandingkan hasil hash di terminal dengan yang tercatat di manifest.json
```

## 4. Prosedur Restore Data

### A. Restore File (Manual via CLI)

Jika ada file terhapus, Anda bisa menyalinnya langsung dari folder backup ke folder storage utama.

```bash
# Pastikan Anda berada di root proyek (atau di dalam container Docker API)
STUDENT_ID=42
BACKUP_DIR=backups/students/${STUDENT_ID}/{timestamp}

# 1. Copy seluruh direktori mahasiswa dari backup ke storage aktif
cp -r ${BACKUP_DIR}/students/${STUDENT_ID}/ storage/students/${STUDENT_ID}/

echo "Restore file fisik mahasiswa ${STUDENT_ID} selesai."
```

### B. Restore Database PostgreSQL

Jika database rusak atau Anda berpindah server, Anda harus melakukan *restore* database.

**Penting untuk Pengguna Docker Baru:** 
Jika Anda baru saja menyalakan Docker di komputer baru (`docker compose up -d`), databasenya akan kosong (muncul error `relation "users" does not exist`). Anda harus membuat struktur tabel terlebih dahulu:
```bash
docker exec dashboard-nusadaya-api-1 bun run db:push
docker exec dashboard-nusadaya-api-1 bun run seed  # (Opsional: untuk akun dummy awal)
```

**Langkah Restore dari file `.sql` (pg_dump):**
```bash
# 1. Copy file backup sql Anda ke dalam container database
docker cp nusadaya_backup.sql dashboard-nusadaya-db-1:/tmp/

# 2. Lakukan pemulihan data menggunakan psql
docker exec -i dashboard-nusadaya-db-1 psql -U postgres -d nusadaya -f /tmp/nusadaya_backup.sql
```

> **Perhatian:** Setelah restore database, pastikan path di tabel `files` (kolom `storage_path`) masih relevan dengan fisik file yang ada di folder `storage/`.

## 5. Disaster Recovery Checklist

Saat terjadi kerusakan sistem total (Server Down/Data Loss), ikuti urutan berikut:

- [ ] Matikan sementara web dan API (`docker compose stop api web`).
- [ ] Identifikasi folder backup terakhir di `backups/full/` dan cek `manifest.json`.
- [ ] Verifikasi checksum beberapa file acak dari manifest tersebut.
- [ ] Restore database PostgreSQL menggunakan file `.sql` terakhir.
- [ ] Kembalikan (*copy*) file fisik dari `backups/full/...` ke folder `storage/`.
- [ ] Nyalakan ulang aplikasi (`docker compose up -d`).
- [ ] Periksa log Redis dan Worker untuk memastikan tidak ada antrean nyangkut.
- [ ] Uji coba unduh file PDF mahasiswa melalui antarmuka web.

---

## Catatan Tambahan
1. **Redis Bersifat Sementara (Volatile):** Jika server mati mendadak, data di Redis (seperti antrean progress) akan hilang, tapi ini tidak merusak data utama. Anda cukup mengulang kembali proses backup yang terputus.
2. **Jangan Merubah File Backup:** File yang sudah berada di dalam folder `backups/` bersifat *Immutable* (tidak boleh diedit manual). Jika diedit, checksum SHA-256 di manifest akan gagal tervalidasi.

## 6. Kebijakan Retensi (Retention Policy)

Untuk mencegah folder backup membengkak tak terkendali, sistem kini dilengkapi **Retention Policy otomatis**.
Penghapusan folder lama terjadi otomatis sesaat setelah backup harian (tengah malam) selesai dijalankan.

**Aturan Penyimpanan (Max Keep):**
- **Full Backup:** Menyimpan maksimal **7 salinan** terakhir.
- **Per Mahasiswa:** Menyimpan maksimal **7 salinan** terakhir per mahasiswa.
- **Per Angkatan & Program:** Menyimpan maksimal **4 salinan** terakhir.

> **Penting:** Sistem retensi hanya menghapus folder yang terbukti valid (memiliki `manifest.json`). File atau folder yang Anda letakkan secara manual di dalam `backups/` tidak akan disentuh oleh sistem penghapus.

## 7. UI Backup & Ekspor Data

Fasilitas baru telah ditambahkan ke Dashboard Web:
1. **Menu Backup & Sistem (Superadmin):** Anda kini bisa melihat riwayat backup, memantau penggunaan storage, dan menjalankan backup secara manual langsung dari menu `Settings > Backup & Sistem`.
2. **Ekspor Semua Berkas Mahasiswa:** Di halaman profil mahasiswa, Superadmin memiliki tombol **"Unduh Semua Berkas"**. Sistem akan mengumpulkan semua file PDF dan foto mahasiswa tersebut, memampatkannya (ZIP), dan langsung menyediakannya untuk diunduh tanpa membebani memori server (Stream).

## 8. Pembaruan Stabilitas, Keamanan, & Fitur (Agustus 2026)

Untuk menyempurnakan sistem, beberapa penyesuaian kritis telah dilakukan:

### A. Penamaan Folder Menggunakan NIM
Struktur folder hasil backup spesifik mahasiswa di dalam file ZIP yang diunduh kini menggunakan **NIM** (misal: `students/NIM123456/...`), bukan lagi ID *database* internal. Hal ini diterapkan di proses ekstrak `copyFileToBackup()` agar Admin jauh lebih mudah membaca dan mencari data di dalam file ZIP. Form Backup Manual per Mahasiswa juga telah diperbarui untuk menerima input **NIM** secara langsung.

### B. Transisi ke Native ZIP (Anti-Crash)
Sistem pembuatan ZIP sebelumnya menggunakan *library stream* NodeJS yang terbukti kurang stabil dan memicu *memory leak* serta *crash* pada *runtime* Bun. Proses kompresi kini dialihkan sepenuhnya ke modul OS bawaan (`child_process` mengeksekusi `Compress-Archive` di PowerShell Windows atau `zip` di Linux). Metode ini terbukti 100% andal tanpa mengganggu *event-loop* API server utama.

### C. Solusi CORS Terintegrasi
Masalah pengunduhan gagal (CORS dan Network Error) telah diatasi sepenuhnya secara permanen. Alih-alih melakukan *fetch* langsung ke *backend* eksternal dari *browser*, antarmuka pengguna kini menggunakan sistem proksi bawaan Next.js (`next.config.ts` rewrites). Permintaan `/api/backups/*` diteruskan secara *server-to-server* menuju API, menjamin tidak adanya hambatan CORS dan mencegah *browser* memutus koneksi di tengah pengunduhan.

### D. Fitur Backup Angkatan & Program Studi
Fitur Backup Manual yang tadinya berstatus *"Coming Soon"* untuk pemilihan **Per Angkatan** (Tahun Masuk) dan **Per Program Studi** kini telah aktif sepenuhnya. UI form telah dilengkapi kotak *input* terkait yang akan meneruskan parameter ke *backend*—karena logika *backend* sebelumnya sudah siap menangani skenario pencarian jamak (*bulk*) ini.

### E. Perlindungan Data Sensitif (.gitignore)
Folder fisik `/storage/` dan `/backups/` telah dikecualikan secara ketat pada `.gitignore` akar proyek. Langkah mitigasi privasi ini memastikan bahwa identitas mahasiswa (KTP, KK, Rapor) dan *dump* basis data secara absolut tidak akan pernah tidak sengaja terunggah ke repositori Git publik maupun *private* di awan.

### F. Perbaikan Health API
Masalah `ERR_EMPTY_RESPONSE` pada saat dasbor meminta laporan status (StorageStatusCard) telah diselesaikan dengan mengubah panggilan dinamis *require* menjadi import statis untuk pustaka *drizzle-orm*, sehingga kompatibilitas modul Bun kembali sehat dan pemantauan sistem *real-time* kembali hidup.
